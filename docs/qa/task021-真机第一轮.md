## 2. P0 缺陷：种子流程存量拿不到训练类型

**现象**：跑完两个种子流程后，「累计 3分7秒 / 2 次」正确，但「按训练类型」三条**全是 0秒 0 次**，两条记录**全部落进「未分类」**。

**根因**（TM 已核代码）：`training_type_id` 只在 `insertSeedRoutine` **新插入**时写入；`repairSeededRoutines` 的逻辑是
```
const missing = SEED_ROUTINES.filter(r => !presentNames.has(r.name));
if (missing.length === 0) return { outcome: 'intact', ... };
```
升级前就已存在的 9 个种子流程全部 present → `missing.length === 0` → **直接 return，永不回填训练类型**。
⇒ **所有存量用户的种子流程永远是「未分类」，统计的分类维度对存量用户等于失效**——本次功能的核心价值（用户原话「拉伸/放松/核心训练各多长时间」）拿不到数。

**TM 拍板方案**（已派 `TASK-021-F1`）：新增 v5 迁移，对「name 命中 9 个种子流程名」**且 `training_type_id IS NULL`** 的行一次性回填；只填空值不覆盖用户已设类型；并把原「不凭名字猜」口径**收窄为「实时新增/复制不猜」**，存量回填允许名字匹配（理由：项目本来就用同一套名字匹配补插缺失种子；即使用户自建同名流程被赋型，也只影响统计归类、不损坏数据）。

**明确不回填历史记录**：`session_history` 的类型是**快照**，V1.3 已砍掉「用户编辑历史类型/日期」，历史不可篡改。老记录留在「未分类」可接受。

## 3. 已知歧义（Reviewer 已查实并修正表述）

`training_type_id IS NULL` 无法区分「从未赋型」与「用户主动清空」。

**【已修正】原表述过于保守**（Research Reviewer 独立查实）：v5 只在**升级那一次启动**执行——`runMigrations` 对 `version <= current` 一律跳过，生产代码**无任何路径重置 `user_version`**（`resetSchema()` 仅 test/qa helper，App 启动链不调用）。
⇒ 「用户主动改未分类会在下次启动被回填覆盖」**不成立**；v5 之后在编辑器选「未分类」保存的 NULL **永久保留**。
真实损失窗口仅限：用户在 v4 构建上设型后改回未分类、再跨 v4→v5 升级这一次。v4 包只装在 QA 机，**现网暴露面≈0**。故**不加标记列**（成本收益不成比例）；若日后产品要求「永久尊重未分类」，走 Change C 一并设计。
